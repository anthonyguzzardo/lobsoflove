# CLAUDE_INDEX.md (LobsOfLove database)

Start here. This folder follows the Dealifier db standard (`../Dealifier/db`): own schema (`lol`), table prefixes,
`<table>_id` keys, `dttm_<event>_utc` timestamps, RLS on every table, every change in BOTH a migration and the
canonical files.

## Folder structure

```
db/
├── CLAUDE_INDEX.md              # THIS FILE
├── sql/
│   ├── dbLOL_Tables.sql         # canonical CREATE TABLE for every table (current state, no ALTERs)
│   ├── dbLOL_Security.sql       # GRANTs, RLS policies, helper functions
│   ├── rpc/                     # rpc_<domain>.sql: rpc_crew.sql (every shared-season write)
│   └── migrations/NNN_*.sql     # deployable change history; the user runs these in the SQL Editor
├── supabase/
│   ├── config.toml              # exposes the lol schema; per-function verify_jwt (always false, commented)
│   └── functions/read-ink/      # AI handwriting reader (index.ts = HTTP, caps, logging; read.ts = model call)
├── tests/try_read_ink.ts        # tries read-ink's model call directly (costs a few cents)
├── types/database.types.ts      # generated by sync-types.sh, never hand-edited
└── sync-types.sh                # regenerate types + copy into ../src/types
```

## Tables

| Table | Kind | Purpose |
|---|---|---|
| `lol.th_ink_reads` | history, server-only | One row per AI read: device, line, chosen action, tokens. Also the daily cap. |
| `lol.tb_crews` | normal | A friend group: name, 6-letter invite code, founder. |
| `lol.tb_players` | normal | A fighter. `user_id` null = pretender (added by name, claimable by `claim_token`). |
| `lol.tm_crew_players` | matrix | Who is in which crew, with role (commissioner, player). One crew per player for now. |
| `lol.tb_matches` | normal | Reported by p1; counts once p2 confirms. Client picks `match_id`. |
| `lol.tb_beacons` | normal | One row per player: the court they are at now. |
| `lol.tb_callups` | normal | "Need N at this court" with a message; open, on (enough in) or off. 12 h life. |
| `lol.tm_callup_players` | matrix | Who a call-up went to and their answer (in, out). |

Writes (rpc/rpc_crew.sql): `fn_save_me`, `fn_create_crew`, `fn_join_crew(code, claim)`, `fn_add_pretender`, `fn_report_match`, `fn_answer_match`, `fn_withdraw_match`, `fn_set_beacon`. rpc/rpc_callup.sql: `fn_post_callup`, `fn_answer_callup`, `fn_cancel_callup`, `fn_delete_crew` (commissioner), `fn_leave_crew`, `fn_remove_pretender`; internal `fn_wipe_crew`. Scenario test recipe: local Postgres 17 with a stub `auth.uid()` reading `current_setting('test.uid')`.

## Edge functions

| Function | Purpose | Secrets |
|---|---|---|
| `read-ink` | One handwritten line -> one app action (Claude, fixed JSON shape) | `CLAUDE_API_KEY`, `LOL_SUPABASE_SECRET_KEY`, `LOL_APP_KEY`, optional `LOL_INK_DAILY_CAP` (400), `LOL_INK_DEVICE_CAP` (60) |

Deploy from `db/`: `supabase functions deploy read-ink --no-verify-jwt`

## Workflow rules

- Schema change: write `sql/migrations/NNN_<desc>.sql` (idempotent, BEGIN/COMMIT, verification SELECTs) AND update
  `dbLOL_Tables.sql` / `dbLOL_Security.sql` / `rpc/`. The user runs the migration in the SQL Editor; then `./sync-types.sh`.
- New table: RLS enabled + policies in Security, plus explicit `service_role` grants (table and sequence).
- Service/secret keys and the Claude key never go in the app. The app only has the URL and publishable key
  (`EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`).
